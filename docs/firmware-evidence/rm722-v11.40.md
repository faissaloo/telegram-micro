# Nokia C2-01 RM-722 firmware 11.40 evidence

This note records facts extracted from the Nokia C2-01 RM-722 firmware bundle used to refine TelegramMicro's device target and SquirrelJME profile. It contains metadata and derived observations only; no proprietary firmware payload is stored in this repository.

## Provenance and integrity

- Source: [Nokia_C2-01_RM-722_V11.40_MIRA.zip](https://androiddatahost.com/wp-content/uploads/Nokia_C2-01_RM-722_V11.40_MIRA.zip)
- Retrieved: 2026-08-10
- ZIP SHA-256: `df91a62d890af9b8272bf26f76a273fd1d5b01203c2ca7ce7b3bb6eb6dd041a8`
- Packing-list timestamp: `2012-10-25T09:19:04Z`
- Variant: RM-722, product code `059F5P7`, software 11.40, EURO-F Hebrew Black

The RM-722 packing list explicitly names the shared `rm721__11.40.mcusw`, `rm721__11.40.ppm_f`, and `rm721__11.40.image_f_059F5P7` payloads. The MCU contains both RM-721 and RM-722 product identities, so those filenames are not by themselves evidence of a mismatched download. All CRC-32 values supplied for the MCU, PPM, content image, DCP, and label image matched their files. The packing-list signatures were not authenticated because the corresponding Nokia verification certificate was not supplied.

## Confirmed device and Java facts

| Surface | Firmware evidence | Safe project conclusion |
| --- | --- | --- |
| Display | DCP `DisplayWidth=240`, `DisplayHeight=320` | Keep the 240x320 target and manifest hint. |
| Java profile | `Profile/MIDP-2.1 Configuration/CLDC-1.1` | The production profile/configuration are correct. |
| Runtime identity | `S40 Adapter: Version 45.15 (PR9.1)`, `CATEGORY_KVM`, `UKVM`, Nokia `impl.isa` packages | Use a narrow S40 PR9.1 firmware profile; do not generalize it to every Nokia KVM or JRT. |
| Default encoding | `microedition.encoding` followed by `ISO-8859-1` | Protocol text must continue to use explicit encodings rather than the platform default. |
| Optional baselines | JTWI 1.0 and MSA `1.0-SUBSET` property tables | These values may be exposed by the narrow emulator profile. |
| Networking | Java socket, server-socket, datagram, HTTP, HTTPS, and SSL implementations and permissions | Raw client TCP is an appropriate transport, but availability is not interoperability proof. |
| Resource failures | Explicit maximum-socket, RecordStore-count, file-handle, thread, and heap failure paths | Preserve bounded models and add physical probes; the firmware did not reveal numeric ceilings. |

The Java surface also contains FileConnection/PIM, Bluetooth/OBEX, Wireless Messaging, MMAPI/AMMS, Location, CHAPI, M3G, SVG, SATSA, and PushRegistry support. Their presence is an API inventory, not authorization to add memory-heavy features without a north-star review.

## Deep-emulation findings

The MCU, PPM, and content payloads are Nokia BB5/XSR flash containers rather than flat ROM images. Each begins with a binary envelope containing `BB5` and `XSR 1.6`, so none is a valid QEMU `-bios` input. The MCU additionally contains `Elf2flash 09.07.000`, `PASUBTOC`, `PAPUBKEYS`, `RAP3NAND`, `GENIO_INIT`, `ISA+DYNSW`, `ISA-USER`, authenticated `Naloext` boot diagnostics, SDRAM discovery, and `MuxOneNAND (CS0)` identification/configuration paths. The content image identifies `Elf2flash 11.51.000` and `CMT PI 299` before the FAT16 volume.

The Nokia service schematic identifies the `3my_30c` board, RAP3Gv4 at `D2800`, and a stacked `D3000` combo containing 64 MB DDR and 128 MB flash. It exposes board connectivity but not the SoC register map, reset vector, interrupt assignments, BootROM, OTP state, or flash-container placement grammar. The public firmware bundle also lacks a verified flat flash reconstruction and per-device protected/calibration data.

These facts make a deep emulator plausible as an incremental reverse-engineering project, but they do not make the image bootable in an existing QEMU Arm machine. See the evidence gates and staged implementation plan in [rap3gv4-qemu-plan.md](../rap3gv4-qemu-plan.md).

## Controls and visual geometry

The firmware contains `KEY_SOFT_LEFT`, `KEY_SOFT_MIDDLE`, `KEY_SOFT_RIGHT`, `KEY_SOFTKEY1` through `KEY_SOFTKEY3`, and `ThreeSoftkeyManager`. Its theme contains left, centre, and right 80-pixel softkey-area assets. The hosted device chrome should therefore expose three physical controls below the LCD:

1. left softkey;
2. centre D-pad/select; and
3. right softkey.

This does not establish that three MIDP commands are simultaneously assigned to those controls. Until a device probe records command labels and key events, the centre control should act as the physical select key and existing semantic left/right command placement should remain unchanged.

Useful native-theme measurements are a 240x38 softkey area, 240x46 status area, 224x60 list selection, 224x30 choice row, 224x34 popup selection, and 215x37 form editor/value area. Nokia Sans resources exist at nominal sizes 8, 12, 16, 20, 24, 28, and 32. These guide density reviews but do not define MIDP `Font` metrics.

## Storage, suite size, and trust-store cautions

The content image exposes a FAT16 layout with 512-byte sectors, 4 KiB clusters, 512 root entries, and a nominal 73 MiB volume. This is a firmware-content image, not a measurement of free user storage or RMS capacity.

Preinstalled JARs range up to 806,847 bytes. That proves only that privileged firmware content can contain suites above TelegramMicro's 512 KiB guardrail; it does not prove equivalent third-party installation or heap headroom. Keep the current artifact limit until the exact release JAD/JAR is installed on-device.

The bundled X.509 database contains 33 roots. As of retrieval, 19 were expired and 14 remained date-valid. The stock trust store therefore cannot be assumed to validate modern public HTTPS chains. TelegramMicro's direct MTProto socket path avoids that dependency, while release instructions should offer USB, Bluetooth, memory-card, or PC Suite installation instead of assuming an on-device GitHub download.

## Still unproved

Static firmware inspection does not prove:

- usable Java heap, allocation failure thresholds, or GC behavior;
- RMS store/record limits or exception ordering;
- key codes, game actions, command placement, or repaint behavior observed by a MIDlet;
- permission-prompt timing or which ports an untrusted suite may use;
- background/resume behavior;
- TLS versions, cipher interoperability, or contemporary certificate validation;
- successful installation, login, or messaging with TelegramMicro;
- the exact RAP3Gv4 CPU model, memory map, reset/boot sequence, or peripheral register behavior; or
- that the BB5 containers can be reconstructed or authenticated without additional BootROM, OTP, and physical-trace evidence.

Run the bounded probes in [runtime-emulation.md](../runtime-emulation.md) and the exact-artifact checklist in [device-proof.md](../device-proof.md) on an RM-721/RM-722 handset running 11.40 before adding behavioral divergences.
